Knowledge Base — Client Record: "Profile" Page
Application: Nexsure (R5 Insurance Agency) — nexui Vue.js SPA Captured from: Client record Clients: Automation_001 URL at capture: https://jmiqaweb01.nexsure.com/nexui/#/entity_console/{orgId}/{clientId}/profile/{subtab} — each Profile sub-tab has its own hash route Captured on: 2026-09-21

Companion document to Client_Overview_Knowledge_Base.md (which documents the client header shared by every Client-level page — the Activate/Deactivate toggle and the New Action / New Delivery / Create Document buttons — not repeated here). This document covers the Profile main tab and its six sub-tabs.

Scope note — what was deliberately NOT exercised: No location/vehicle/named-insured/relationship/classification record was actually created, edited or deleted — every "Add New" / "New ___" form opened here was cancelled. Update Bill To and Delete (on the Locations "Manage" grid) were not clicked.
1. Layout: Profile replaces the second tab row with its own sub-navigation
Selecting PROFILE on the main tab bar swaps the client-wide second-row tabs (Actions / Deliveries / Attachments / Phone Log, documented in the Overview KB and in Policy_Details_Knowledge_Base.md) for six Profile-specific sub-tabs: Items (default), Profiling, Demographic Data, Related Accounts, Classified, Campaigns.

Important UI quirk: the client-wide "ACTIONS" tab is still visibly rendered at the far left of this second row (its own DOM link, href="#/entity_console/{org}/{client}/actions"), but Deliveries, Attachments and Phone Log are not visually rendered at all while a Profile sub-tab is open — they never appear, not even truncated. Inspecting the page (read_page) confirms all three still exist as real, working <a> links in the DOM (.../deliveries, .../attachments, .../phone) — they are simply not drawn in this row's layout when Profile's own 6-item sub-nav is present, apparently because Profile's sub-nav is wider than Policies' equivalent group and pushes them out with no overflow/scroll affordance. Automation implication: don't rely on visually finding the Deliveries/Attachments/Phone Log tabs while on a Profile sub-tab — navigate to them directly by hash URL, or switch to Overview/Policies first where they render normally.
A recurring server error was observed loading Profile > Items in this test session: "An unexpected error occurred. Please contact Nexsure Support and reference issue #260782904." — a third distinct reference number, different from the bind-error (#260782741, see Opportunity_Marketing_Page_Knowledge_Base.md §6.7) and the Policy-Detail-page load error (#260782822, see Policy_Details_Knowledge_Base.md §7). As with those, the underlying page still rendered and worked correctly underneath the toast once dismissed.
2. Sub-tab: Items (default)
A 2×2 dashboard of record-type panels, each following the identical pattern — a panel header, an "+ Add New" button, a "Manage" button (with its own type-specific icon: location pin / people / car / person), and (if the client has records of that type) a small inline preview grid:

Locations — "1 record saved" in this test. Inline grid columns: Primary (✓), Status (e.g. "A" for Active), Location Name, Address (linked to Google Maps, matching the pattern in the client header), City, State/Prov, Zip/Postal, In Use, plus a trash/delete icon per row.
People — "1 record saved". Inline grid columns: Primary, Status, Name (linked, with a small contact-card icon and a second small icon after it), Title, Contact (a mail icon), In Use, delete icon. The one row seen ties back to the client's main Contact ("Automation_001 Test").
Vehicles — empty in this test, rendered with the "There are no items to display. / If this is unexpected, please contact your system administrator." empty-state style (same style already catalogued in Policy_Details_Knowledge_Base.md §9).
Named Insureds — "1 record saved". Inline grid columns: Primary, Status, Named Insured (e.g. "Automation_001"), FEIN/SS#, Primary NAICS, In Use, delete icon.
Top-right of the whole Items page: an All / Active Only toggle (defaulted to "Active Only").
2.1 "Manage" → a full grid page (not a modal)
Clicking Manage on any panel navigates (via breadcrumb, e.g. "Profile > Items > Locations") to a dedicated full-page grid, not an in-page modal — this differs from "Add New," which does open a modal (§2.2). The Locations "Manage" page has:

A drag-and-drop "Drag a file here to import or click to browse" zone, an Export button, a "+ New {Type}" button (e.g. "New Location"), a "$ Update Bill To" button, and a red "× Delete" button — this same toolbar is duplicated above and below the grid.
Show Filters toggle.
Grid columns for Locations specifically: a bulk-select checkbox column, Primary (✓), Billing, an unlabeled "☂"-style icon column (purpose not confirmed — possibly an underwriting/liability marker), Location Name, Address (linked), City, State/Prov, Zip/Postal, Phone Number, Fax Number, Status. Standard Showing/Items-per-page/Locked-Unlocked/Page-X-of-Y pagination footer, duplicated top and bottom.
Expect the People / Vehicles / Named Insureds "Manage" pages to follow the same toolbar-plus-grid shape with type-appropriate columns and a type-appropriate "$ Update Bill To"-equivalent action; not individually captured in this pass.
2.2 "+ Add New" (Locations) → the "New Location" modal
An in-page .dynamicModal (not a new tab/popup/iframe):

Location Information: Location Type* — a searchable dropdown with 9 options: Home Office, Rental Property, Primary Residence, Vacation Residence, CRM QA Office, Mailing Address, Travel Station, INACTIVE Personal Location, UNUSED Personal Location (the "CRM QA Office" and "INACTIVE/UNUSED Personal Location" entries are clearly test-environment-specific values, not a stock list). Location Name (free text). Primary Location / Billing Location checkboxes.
Three sub-tabs: Address* (default), Underwriting, Contact Information (the latter two not explored in this pass).
The Address sub-tab has side-by-side Physical Address and Mailing Address blocks (Address Line 1*, Address Line 2, City*, State/Province*, Zip/Postal*, County, Country dropdown, International Address Info, a "Verify Address" button each) plus a "Same as Mailing Address" checkbox. Quirk observed: checking "Same as Mailing Address" visibly relabels both address blocks with a small "⊘ Not Deliverable" badge next to their headers and defaults both Country dropdowns to "United States" — the exact interaction between the checkbox and which side becomes read-only was not fully traced in this pass; worth re-verifying carefully before automating this form.
Footer: "ADD ANOTHER" checkbox, Save Location / Cancel buttons.
3. Sub-tab: Profiling
A single long form, not a grid — profile/underwriting-style attributes about the client, with a Save button (disabled until a field changes). Notably, the form's fields change based on the Client Type, confirmed by watching the page re-render after its data finished loading:

Profiling Information: Client Type dropdown (options include at least Commercial and Personal — this test client is actually set to "Personal," even though every other document in this series refers to it via a "Commercial Lines" Opportunity and a "General Liability - Commercial" policy; worth flagging as a real data inconsistency in this sandbox, not an app defect) and Enterprise Code (free text, populated here as "0QA10306").
Source: Referred By dropdown (defaulted "Please select..."), Account Notes (free text).
When Client Type = Personal, the form shows an "Auto Information" section (No of Drivers, No of Young Drivers, No of Vehicles, No of Accidents, Zip Code) followed by a "Residence Information" section (Home — a dropdown, Residence County, Sq. Feet of Home, Distance from Fire Hydrant, Miles from Fire Department, Fire District, Construction, No of Locations).
(Not directly observed, inferred from the page's initial/placeholder render before data loaded): when Client Type = Commercial, the equivalent section appears to be "Organization Information" (Legal Entity Type, Business Start — a date picker, No of Employees, No of Locations, No of Vehicles, Estimated Annual Gross Sales, Estimated Commission, Monthly Payroll) instead of Auto/Residence Information. Automation implication: this form is conditionally rendered based on Client Type — do not assume a fixed field set; read Client Type first, then branch.
4. Sub-tab: Demographic Data
A plain full-page grid with a "+ New Record" button and a red "× Delete" button (top right), a Showing/Items-per-page/Locked-Unlocked/Page pagination bar, and no visible filter control. Empty in this test client, using the "There are no items to display..." empty-state style. This tab took noticeably longer to finish loading (several seconds of spinner) than most other grids in this app — worth a generous wait/poll timeout if automating against it.
5. Sub-tab: Related Accounts
A grid with "+ New Relationship" and "× Delete" buttons (top right) and a Show Filters toggle. Empty in this test client ("There are no items to display..."). This is presumably where the client-header's "Related Account: 0" stat (documented in the Overview KB) is managed/sourced.
6. Sub-tab: Classified
A grid with a "+ New Classification" button (top right, no Delete button visible) and the standard Showing/Items-per-page/Locked-Unlocked/Page footer. Empty in this test client. Minor inconsistency noted: this grid's pagination footer read "Page 1 OF 0" once fully loaded, whereas the otherwise-identical-looking empty grids on Demographic Data and Related Accounts both read "Page 1 OF 1." Not investigated further, but worth knowing the "OF" page-count value isn't consistently computed across these empty grids.
7. Sub-tab: Campaigns
A grid with only a Show Filters toggle — no "+ New" / Add button of any kind was present here, unlike every other Profile sub-tab. This suggests Campaigns is a read-only view (campaign enrollment presumably happens from a Marketing/Campaigns module elsewhere in the app, not from the Client record). Empty in this test client, same "There are no items to display..." style.
8. Summary checklist for automation design
Deliveries / Attachments / Phone Log tabs disappear visually (but not from the DOM) whenever a Profile sub-tab is active — a genuine layout quirk, not a permissions issue. Automate against the hash URL directly if you need those tabs while working within Profile.
A third distinct server error code (#260782904) was observed on this page, on top of the two already logged elsewhere (#260782741, #260782822) — reinforces the pattern that this QA environment throws a toast-level "unexpected error" fairly often on page/tab loads while still rendering correct data underneath. Don't treat any single error toast as fatal without checking the DOM/grid state.
"Add New" opens an in-page modal; "Manage" navigates to a full page. These are two different UI patterns for what looks like the same underlying record type — don't assume both open the same kind of surface.
The Profiling tab's field set depends on Client Type (Personal → Auto/Residence Information; Commercial → inferred Organization Information) — read Client Type before deciding which fields to expect/fill.
This test client's Client Type is "Personal," despite carrying a "Commercial Lines" Opportunity and a "General Liability - Commercial" policy elsewhere in the same record — a data inconsistency worth being aware of if cross-referencing Client Type against Opportunity/Policy Line-of-Business elsewhere in automation.
Demographic Data's grid loads noticeably slower than sibling grids on this page — build in extra wait tolerance.
Of the six Profile sub-tabs, Campaigns is the only one with no create action — treat it as read-only in automation design unless a different environment shows otherwise.
