# Knowledge Base — Client Record: "Claims" Page (client-level)

**Application:** Nexsure (R5 Insurance Agency) — `nexui` Vue.js SPA
**Captured from:** Client record `Clients: Automation_001`
**URL at capture:** `https://jmiqaweb01.nexsure.com/nexui/#/entity_console/{orgId}/{clientId}/claims`
**Captured on:** 2026-09-21

This is the client-level **Claims** tab — distinct from the Policy Detail page's own "Claims" sub-tab (documented in `Policy_Details_Knowledge_Base.md` §5.4, which showed a plain "No records found." message). This page was **empty** for this test client — no claims of either kind exist on Automation_001. It is, structurally, the single most interesting page found across the Client-level tabs.

> **Scope note — what was deliberately NOT exercised:** since no claim exists on this client, no claim detail screen could be opened, and the "carrier claims" sub-tab's "Open" report button was not clicked (to avoid an uncontrolled new-tab/report action with an unconfirmed effect).

## 1. A genuinely different sub-system: the "claims" sub-tab is a legacy page rendered inside an `<iframe>`

The Claims page has **two small lowercase sub-tabs directly under the "Claims" header: "claims" (default) and "carrier claims"** — styled completely differently from every other tab in this app (small, lowercase, plain-text tab labels rather than the app's usual bold uppercase tab chrome). This is the first visible clue that something different is going on, and it's confirmed by inspecting the DOM:

- **The "claims" sub-tab's entire content area is a single `<iframe>`**, `src` pointing to **`/setup/TransferSessionPolicy.asp`** on the same host — a classic **classic-ASP (.asp) page**, not part of the Vue SPA at all. It's loaded via a session-transfer URL carrying an auth token, i.e. this is an older/legacy claims module being embedded wholesale into the modern app shell.
- Visually this shows immediately: the filter panel uses old-fashioned grey `<table>`-based layout, small native `<select>` dropdowns, bare "..." picker buttons, and classic ASP.NET Web Forms-style field names — confirmed via the iframe's own DOM: form field names like **`filter$ClaimStatusId`**, **`filter$ClaimStage`**, **`filter$SortField1`**, etc. (the `$` separator is the hallmark of ASP.NET Web Forms naming). None of this matches the Vue component styling used everywhere else in `nexui`.
- **Search Filters** on this legacy page: **Claim Status** (native select — **3 options: All, Open, Closed**, defaulted to "Open"), **Claim Stage** (native select — **12 options: All, Adjustor Assigned, Carrier assigned adjustor, Claim Re-Opened, Commercial LOB Claim, EPO 1.94 build 4, New claim stage 1.94 build 4, New claim stage 1.94 build 8, Pending Assignment, Personal LOB Claim, Subrogation, Test 2.1 build 4 claim stage** — several of these are obviously QA/test-environment artifacts, e.g. "EPO 1.94 build 4" and "Test 2.1 build 4 claim stage," confirming this list is admin-configurable per agency), Issuing Carrier, Claimant, Claim No., Eff. Date (From/To, each with a small calendar-icon picker), Exp. Date (From/To), Date of Loss (From/To), Business Type(s) (with a "..." browse button), Retail Agent, Adjustor, LOB, Policy No.
- **Sort Filters:** Sort Field 1 / Sort Order 1, Sort Field 2 / Sort Order 2 — Sort Field options: Adjustor Name, Claimant Name, Claim Number, Claim Stage, Claim Status, Date of Loss, Eff Date, Exp Date, Issuing Carrier, Line of Business, Paid Amount, Policy Number, Retail Agent, Reserve Amount, Taken By. Sort Order options: Ascending, Descending (Sort Field 1 defaulted to "Date of Loss" / "Descending").
- **Search** / **Clear** buttons, a **"Save Filter Settings"** checkbox, a **"Showing Page 0 of 0"** counter with first/prev/next/last navigation icons, and — in this test with zero claims — the message **"Filter result found no record(s). Please modify search criteria and try again."** The sub-tab links are duplicated at both the top ("Filters: [Hide]") and bottom ("carrier claims | claims") of the panel.
- Switching to **"carrier claims"** and back triggers a **full reload of the iframe content** (a classic-ASP-style postback, not a client-side re-render) — automation should expect a real navigation/load event here, not an instant SPA state change.

## 2. "carrier claims" sub-tab — back to modern Vue styling

In contrast, **"carrier claims" renders as an ordinary Vue component**, matching the rest of the app: *"Carrier Claims / 0 items matched filter settings."*, a **"Select Claims Report"** dropdown (a custom component, not a native `<select>` — its options couldn't be enumerated via direct DOM inspection in this pass) plus an **"↗ Open"** button (the external-link-style icon strongly suggests this opens a report in a new tab, consistent with how carrier-level claims reporting likely works — not confirmed by clicking), a **Show Filters** toggle, and a skeleton-bar empty grid (the same at-rest empty style already catalogued for the Opportunity Marketing Quotes grid in `Opportunity_Marketing_Page_Knowledge_Base.md`).
- Its filter panel: **General** (Program, Carrier Name), **Dates** (Transaction Effective Date From/To with "±DAYS" quick-offset buttons, Date of Loss From/To with "±DAYS" buttons), **Amounts** (Claim Amount Incurred From/To, Indemnity Reserves From/To), plus Loss Description (text) and Status (dropdown, default "Any"). **Apply Filter** / **Clear Filter** buttons, **Save / Recall / Clear History** preset links (note: "Clear History" here vs. "Clear Memory" on most other filter panels in this app — a small naming inconsistency worth knowing about if automation matches on button label text).

## 3. Summary checklist for automation design

- **The "claims" sub-tab is not part of the Vue SPA at all — it's a classic ASP page loaded in an `<iframe>`** (`/setup/TransferSessionPolicy.asp`), with entirely different visual styling, native HTML form controls, and ASP.NET Web Forms field-naming conventions (`filter$FieldName`). Any automation targeting claim search/filtering on this specific sub-tab needs to operate inside that iframe's document (switch frame context), not the outer page — very different from every other grid/filter pattern documented across this whole KB series.
- **"carrier claims," by contrast, is an ordinary modern Vue component** — the two sub-tabs of the same "Claims" page are built on two completely different technology stacks. Switching between them triggers a real content reload, not an instant tab-swap.
- The Claim Stage list on the legacy claims iframe (12 options, several clearly test/QA artifacts like "EPO 1.94 build 4") confirms claim stages are agency-configurable data, not a fixed enum — don't hard-code an expected stage list without checking the target agency's actual configuration.
- The **"↗ Open" button next to "Select Claims Report"** on Carrier Claims looks like it opens a generated report in a new browser tab — worth confirming and handling multi-tab/window automation for that specific action if it needs to be exercised.
