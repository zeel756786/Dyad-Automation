Testing Process Notes — standing rules for this QA knowledge-base project

This file isn't a page of the ALIS app like the rest of this knowledge base — it's the operating rules for how testing passes against ALIS are run and documented. Read this first, before starting any new instruction from the user, especially after a break, a compaction, or picking work back up after several other pages have been documented.

Rule 1 — every new instruction starts from brand-new data unless the user says otherwise
When the user gives a new instruction to test a flow, screen, or feature, the default is: start from a brand-new Insured and Submission, created fresh via login → Clearance Search → +New Insured (see `login.md`, `header.md`, `new-insured-form.md`). Do NOT navigate back into an existing/previous submission, quote, or option to "continue" testing unless the user's instruction is explicitly a continuation of that same submission (e.g. "go back to that same quote and change X"). If there's any ambiguity about whether an instruction means "continue on the existing data" or "start fresh," the default assumption is start fresh — re-using existing data (especially anything already bound/approved, or anything from a prior, separate test pass) is the mistake to avoid, not the safe default.

This matters more once an option has been through Bind & Invoice (see `bind-and-invoice.md`): a bound option is no longer a "clean" testbed. Its Premium-tab fields, status, and downstream records (policy number, invoice, Policy Generation) are all now live consequences of that specific bind — going back into it to tweak fields "for the next test" mixes two different tests together and makes both harder to document cleanly. If the user asks for further changes to an already-bound option specifically, that's fine — but it's a distinct, explicit instruction, not the default next step after a bind completes.

Rule 2 — when told to "start from scratch" / "start from login," take it literally
That means: actually return to the login screen (or use the avatar-menu Logout, then log back in — see `header.md`) and perform the full flow again from the top — new Insured, new Submission, new Quote, and onward — rather than reusing anything from the in-progress browser tab's current state. Don't interpret it as "keep working in the same tab, just navigate to a fresh-looking screen."

Rule 3 — capture new findings into the knowledge base as they happen, not just at natural stopping points
Every screen/action gets its own markdown file mirroring the real framework repo's `alis/knowledge/pages/` folder structure, written in plain language, with: what the screen is and how it's reached; the fields/behavior actually observed; explicit verification results against whatever reference data the user supplied; a caution that rated amounts/dates/form lists are a snapshot of one test pass, not fixed constants; and an "open items" list for anything not exercised. Cross-link related pages (e.g. `quote-option-detail.md` ↔ `bind-and-invoice.md` ↔ `rate-summary.md`) rather than duplicating content.

Rule 4 — a UI element that appears to do nothing may just be showing a toast you missed
Several ALIS validation messages render as a toast that fades in 1–2 seconds with no lingering visual cue. Screenshot immediately after a click, not after a multi-second wait, before concluding a button is broken — see `bind-and-invoice.md` for the full writeup of this pattern, which cost significant time to diagnose once already.

Rule 5 — after any action with visible side effects (a bind, a save, a status change), check for new tabs/popups before moving on
This app has triggered new browser tabs (a "Policy Generation" popup) and in-page modals (a "Popup Notes" system-note popup) automatically as side effects of actions like Bind & Invoice, without any click specifically requesting them. Call the tab-context tool and take a screenshot after any state-changing action, not just after actions that are expected to open something.

Rule 6 — on a type-ahead with more than one visible suggestion, click the suggestion directly; don't trust keyboard Down+Return
Earlier passes found that a mouse click on a type-ahead suggestion "did not reliably register" on this instance and that keyboard selection (Down arrow, then Return) was the reliable method — see the environment-variant notes in `new-insured-form.md` and `add-quote.md`. A later pass (2026-09-23) refined this: keyboard Down+Return is reliable only when the search produces a SINGLE suggestion (confirmed for a City/State/Zip search and a Coverage search, both single-match). When a search produces multiple suggestions, keyboard Down+Return unreliably selects the wrong (usually second-listed) item — confirmed twice in the same pass: an Agency search for "ABC Insurance" (2 near-duplicate matches — see `new-insured-form.md`'s "Agency autocomplete can return near-duplicate matches") landed on the wrong one, and a COB search on an empty-focus full list (6+ matches) also landed on the wrong one. The fix both times was to clear the field, retype, and click the correct visible suggestion directly with the mouse — this worked reliably. Net rule: for a single-match type-ahead, keyboard selection is fine; for a multi-match type-ahead, clear and use a direct mouse click on the specific suggestion you want, and read its full label (including any code in parentheses) before clicking, since near-duplicate entries are common in this app's data.

Rule 7 — on a screen with two stacked Save/Cancel button pairs, click the LOWER one
The Add/Edit Risk screen's Limits/Deductibles tab (on the "dyad" `customer-alis.dyadtech.com` instance — see `add-edit-risk.md`) shows two Save/Cancel pairs stacked at the bottom of the page: an upper pair (saves the embedded Additional Insured panel) and a lower pair (saves the Limits/Deductibles values themselves, confirmed by its own "Limits/deductibles saved Successfully" toast). A pass on 2026-09-23 found that clicking the UPPER Save button was associated, twice, with the browser tab becoming fully unresponsive for 30–60+ seconds and then self-closing, with the entered data lost (not persisted) both times — a real, reproducible freeze tied to that specific button on this specific page, not a scripting mistake. Per explicit user instruction, click only the LOWER Save button to proceed; this was used for the remainder of that pass with no further freezes, and the save was confirmed to persist. If the upper Additional Insured panel genuinely needs its own save, expect this risk and be ready for the tab to need reopening.

Rule 8 — the Terms & Forms "keep" count is the reference list's own item count, full stop — don't assume an unflagged extra form is fine to leave
Earlier passes (see `quote-option-detail.md`) mistakenly concluded that a leftover state-specific auto-attached form (e.g. IL 02 60 for Connecticut, IL 02 82 for Mississippi) — present after deleting every form on the "should be removed" reference list, but not itself named on either reference list — was fine to leave attached, since the resulting count (29) was "explained" by it. This was corrected by explicit live instruction on 2026-09-23: the real target is exactly the "should be present" reference list's own item count (28 in the passes so far), and ANY extra form beyond that — flagged on a reference list or not — should be deleted too. The Policy Generation "Review Policy" flow's "Missing Forms" tab (see `policy-generation.md`) is one reliable way such an extra form can surface (a physical-copy-missing flag), but don't wait for that flag or assume it's exhaustive — after deleting the reference "should be removed" list, count what's left and delete anything beyond the "should be present" list's own count.

Rule 9 — a Policy Number entered in the Bind & Invoice modal must be unique on every single attempt, no exceptions
Never reuse a Policy Number from an earlier attempt — not for a retry, not for a re-bind of the same option after it was edited or its bind was undone, not for anything. Generate a fresh one every time (this project's convention: `POL` + submission number + a `date +%y%m%d%H%M%S` timestamp). See `bind-and-invoice.md`'s "HARD RULE" for the confirmed case where the same option (SUB000863-01) needed two genuinely different Policy Numbers across two separate binds in the same session, and Rule 1 above's note on why re-touching an already-bound option is a distinct, deliberate action in the first place.

Rule 10 — the virtualized Terms & Forms grid's mouse-wheel scroll getting "stuck" is a recurring, confirmed issue; use keyboard Home/End instead, and re-verify every checkbox state after any stray click
Confirmed a second time on an independent autonomous pass (2026-09-23, SUB000864-01): repeated mouse-wheel scroll attempts on the Terms & Forms Forms grid, at varying coordinates and scroll amounts, stopped advancing the visible row window partway through the list — the exact same symptom as the first documented occurrence (see `quote-option-detail.md`). The reliable fix, confirmed again: click any row once to focus the grid, then press the keyboard `Home` or `End` key to jump straight to the top or bottom of the true virtualized list — this worked instantly both times, where continued mouse-wheel scrolling did not recover.

A sharp-edged consequence of the "click a row to focus it" step: clicking anywhere on a row's body (not just its own Delete checkbox) silently toggles that row's checkbox — confirmed AGAIN this same pass, twice in a row, on two different rows (L343, then S013), each time as a direct side effect of a click made purely to focus the grid before pressing Home/End, with no intention of touching that row's checkbox at all. Both were caught immediately by screenshotting right after the click and fixed by clicking the actual checkbox cell to toggle it back — but this is a standing trap, not a one-off: treat every click anywhere in this grid (not just clicks aimed at a checkbox) as a potential checkbox-toggle, and always screenshot and re-verify the checkbox column immediately afterward, especially right before an irreversible action like "Delete Form."

This same pass produced a real, live example of what happens when that verification step is skipped: an earlier stray click (made to defocus/click blank space) landed on an unrelated row (CG0001, "CGL COVERAGE FORM" — the option's base coverage form, not one of the 10 forms actually meant to be deleted) and silently ticked its Delete checkbox; this went uncaught because the checkbox state wasn't re-screenshotted before clicking "Delete Form," and the form was deleted alongside the 10 intended ones, dropping the Forms count to 27 instead of the correct 28. Recovery workflow, confirmed working: "Add More Forms" button (top-right of the Forms grid) → "Add Forms" modal → click "Advanced Filter" to reveal a Form Code "Contains" text field (separate from the basic Company/Coverage/COB/State criteria and the Optional/Mandatory/All filter radios shown by default) → type the exact form code (e.g. `CG0001`) → "Search" → the matching form appears in the "All Forms" results grid (its "Is Mandatory" flag, if any, doesn't block re-adding it even via the default "Optional" filter — using "All" or the Advanced Filter's own Form Code search bypasses that filter entirely) → tick its row checkbox, which moves it into the "Selected Forms" section below → scroll down to the modal's own bottom bar → "Add To Quote" button (not "Save" — the modal has no button literally labeled "Save") → modal closes and the Terms & Forms count updates immediately (27 → 28, confirmed). Note the re-added form is appended to the END of the Forms grid (last row, after the alphabetically/code-sorted original forms) rather than being reinserted at its original position in the list — this doesn't affect the generated Policy Generation PDF's Schedule of Forms or forms count, both of which picked it up correctly, but don't expect the grid's row order to be restored to exactly what it was before the accidental deletion.
