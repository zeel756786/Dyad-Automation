Bind & Invoice (ALIS)

Overview
"Bind & Invoice" is one of the five action buttons in the bottom bar of the Quote Option Detail page (see `quote-option-detail.md`), alongside Generate Quote, Generate Indication, Proceed to Bind, and Save — in that left-to-right order, with Bind & Invoice second from the right. It is the action that actually binds the option and generates its first invoice — this is a real, irreversible write: once completed, the option's status becomes "Bound" and a real invoice record is created (see "Confirmed successful run" below). Only ever exercise it on test data you're prepared to leave bound; per the project's standing rule, that means a freshly created submission/quote, never one you might want to keep rating or re-testing afterward.

Reached via
Quote Option Detail page → any tab → bottom action bar → "Bind & Invoice" button → clears two Premium-tab validations → opens the "Bind & Invoice" modal → select a Policy Method and (if Manual) enter a policy number → "Proceed" → on success, navigates to a new Billing screen showing the generated invoice.

CAUTION — this button's validation messages are shown as a transient toast that is very easy to miss
Every validation step in this flow (the Premium-tab checks before the modal opens, and the Policy-Method check inside the modal) surfaces as a yellow/red toast in the top-center of the page that fades on its own after roughly 1–2 seconds. A screenshot taken even 2–3 seconds after the click will show nothing — the page looks like it did nothing at all, with no lingering visual cue (no red border, no inline error text near a button). This is exactly what made the button look completely broken on the first pass through this flow: repeated clicks with 2–6 second waits before screenshotting never caught the toast, and looked identical to a dead button. If a button click in this app appears to do nothing, screenshot immediately (within well under a second) before concluding it's a no-op — check the console/network log too; a "successful" click with a validation failure still fires no new network request, exactly like a genuinely broken button would, so the toast is the only tell.

Step 1 — Premium-tab validation (must be cleared before the modal will open)
Clicking "Bind & Invoice" first validates the current option's Premium tab. In this pass, two fields were flagged, both empty/unset defaults left over from rating:
- "Please Enter TRIA Premium" — the Premium tab's TRIA Type was "Applied" but TRIA Premium $ was still $0.00. Typing an explicit `0` into the field and tabbing out did NOT clear this validation — it requires a genuinely non-zero amount. Entering a small nominal test value (typed as "100", which the field's input handling actually stored as $10.00 — see caution below) turned the field's outline green and cleared the validation.
- "Please select Commission/Agreement for Agent Commission" — the Agent Comm % field showed "[]" (no agreement selected), while the neighboring Gross Comm % already showed "[GLOBAL DEFAULT]" at 20.00. The Agent Comm % dropdown offered three choices: Special Agency Commission, AGT007 (the agency code), and GLOBAL DEFAULT. Selecting GLOBAL DEFAULT auto-populated the field to 10.00 and cleared the validation immediately (no typing needed, and no extra click required beyond picking the option).

CAUTION — the TRIA Premium $ field appears to drop a digit when typed via automation
Typing "100" into TRIA Premium $ (after double-clicking to enter edit mode, Ctrl+A to select the existing value, then typing) resulted in the field storing $10.00, not $100.00 — confirmed by zooming in on the rendered value with no cursor overlapping it. The field's green (valid) border and the header's live TRIA total ($10.00) both confirmed this was the actual stored value, not just a display artifact. Whether this is a formatting/masking quirk in the field itself or an input-timing issue, don't assume a typed numeric value lands verbatim in this field — re-check the rendered value (zoomed, without the cursor over it) after typing into it.

Once both fields validate, the header's TRIA figure updates live (e.g. $0.00 → $10.00), Total Amount updates accordingly, and the Fees $ field briefly shows a small recalculation spinner.

Step 3 — "Proceed" also validates, and reveals more required fields step by step
Clicking "Proceed" with no Policy Method selected throws another transient toast: "Please select policy method." Selecting "Policy Number" reveals two further sub-radio options that are NOT visible until Policy Number is chosen: "Manual" and "Policy Register" (presumably: type a number yourself, vs. pull one from a managed registry — Policy Register was not exercised this pass). Selecting "Manual" reveals a required "Policy Number" text field (empty by default, red-bordered until filled). This is a second instance of a UI pattern worth remembering from elsewhere in this app (see `add-edit-risk.md`/`quote-option-detail.md`'s own timing cautions): fields can be conditionally revealed by a radio choice, so what a form "requires" isn't fully visible until you start selecting options.

HARD RULE — Policy Number must be unique on every single bind attempt, confirmed and reiterated by explicit live instruction
Never reuse a Policy Number typed into a previous Bind & Invoice attempt, even for the exact same submission/option and even if that previous bind failed, was undone, or the option is being re-bound after edits. Generate a fresh value every time (this document's convention: `POL` + submission number + a `date +%y%m%d%H%M%S` timestamp, e.g. `POL863260923091923` then `POL863260923092853` for two separate binds of the same option SUB000863-01 later in the same session). Treat this the same as any other required-unique-value field in this app (compare the Full Name-uniqueness rule for Insureds in `new-insured-form.md`) — don't assume the field will silently reject or dedupe a repeat value; just never offer one.
